## Q001：为什么补码不是“负号加绝对值”？

- 提问日期：2026-10-07（Asia/Shanghai）。

- 出处：主讲义 D1-E1 末段，已与用户截图核对；截图文件名为「截屏2026-10-07 10.15.23.png」。该段是助手编写的教学说明，不是教材原文。知识点属于原课程第2讲的整数表示；本条未核对原课件页序及教材印刷页码、PDF页序，均待核实。
- 本条解答性质：助手补充，采用固定位宽的补码位模型，不是在执行 C 表达式。

截图原文：

> “取反加一”是在固定位宽里构造相反数的便捷方法，不是负号占一位、剩下七位写绝对值。`1000 0001` 在 8 位补码中不是 −1。解题时写清位宽，再使用这条方法。

### 先理解 `1000 0001` 为什么不是 −1

“补码”是一套用 0 和 1 表示整数的规则。不能把它理解为“第一位写负号，后面七位写绝对值”。绝对值就是去掉正负号后数的大小，例如 −37 的绝对值为 37。

初学时可能自然地这样读：

```text
1  |  0000001
负号    数字 1
所以是 −1？
```

这种“符号加绝对值”的思路叫原码。补码采用另一套规则：每个位置都有数值权重，8 位补码最左边那一位的权重是 −128。

| 从左到右的8个位置 | 第1位 | 第2位 | 第3位 | 第4位 | 第5位 | 第6位 | 第7位 | 第8位 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 这一位是1时贡献的数值 | −128 | 64 | 32 | 16 | 8 | 4 | 2 | 1 |
| `1000 0001` 的各位 | 1 | 0 | 0 | 0 | 0 | 0 | 0 | 1 |

读表方法：哪一位是 1，就把该列对应的数值加进来；是 0 就不加。表中的“第1位”等只是从左到右数位置，不是主讲义从右边开始的位编号。

因此，`1000 0001` 的8位补码值为 **−128 + 1 = −127**。

最左边的 1 确实能告诉你“这是个负数”，但计算数值时，它贡献的是 −128，不能只把它当成一个负号。后面七位共同表示的是要加在 −128 上的数，不是整个负数的绝对值。

### −1 的8位补码是什么？

是 `1111 1111`。按上表相加：

**−128 + 64 + 32 + 16 + 8 + 4 + 2 + 1 = −1。**

也可以用“取反加一”得到：

```text
+1：       0000 0001
每一位取反：1111 1110   ← 0变1，1变0，包括最左边那位
再加1：    1111 1111   ← −1的8位补码
```

“相反数”就是正负相反的两个数，例如 +1 和 −1、+37 和 −37。“取反加一”帮助我们算出相反数对应的整串位，不是只改最左边一位。

### 联系例题中的 −37

```text
+37：      0010 0101
取反：     1101 1010
加1：      1101 1011   ← −37的8位补码
```

读回来，取位值为1的位置相加：

**−128 + 64 + 16 + 8 + 2 + 1 = −37。**

这里后面七位 `1011011` 按非负二进制数读是 91，并不是绝对值 37；整个数是 −128 + 91 = −37。

### 为什么先写清位宽？

位宽就是总共使用多少个二进制位。“取反”之前，要知道有多少位需要翻转。例如，同样表示 −1：

```text
4位：+1是      0001 → 取反      1110 → 加1      1111
8位：+1是 0000 0001 → 取反 1111 1110 → 加1 1111 1111
```

对于 w 位补码，最左边一位的权重为 −2^(w−1)。因此4位时是 −8，8位时是 −128，不能把8位的权重直接用于其他位宽。

先掌握两个动作：**把正数变成对应负数的补码，用固定位宽的“取反加一”；读一个8位补码，用“−128、64、32、16、8、4、2、1”这些权重相加。**

这里的 ±1、±37 都在8位补码范围内。边界例外是 −128：它的相反数 +128 超出8位补码范围。对 `1000 0000` 取反加一并只保留8位，会仍得到 `1000 0000`，不能说8位补码因此能表示 +128。

## Q002：截断为什么会改变数值？C、实现定义和 x86 截断模型是什么意思？

- 提问日期：2026-10-07（Asia/Shanghai）。
- 用户指定位置：复习第1讲，4.2「扩展与截断：先决定保留什么」。
- 用户原始问题：
  1. “如果表示为0xDB 那不是和0x12DB表示的数不一致了吗”
  2. “C指的是什么 什么是实现定义”
  3. “x86补码截断模型是什么”
- 出处：主讲义4.2第二段，已与用户截图核对；截图文件名为「codex-clipboard-f2ae7443-98af-4f67-a004-a46ca8ef47ff.png」。对应原课程第2讲的整数转换；教材对应2.2.7（截断数字），具体教材印刷页码、PDF页序与课件精确页序待核实。语言规则另核对 C11 标准草案 N1570 的3.4.1、3.4.3、6.3.1.3和GCC官方文档，不能把标准草案页码当成教材页码。
- 解答性质：助手补充。机器示例采用本课程 x86-64/Linux 环境、8位字节及补码整数；C语义说明采用教材所依据的传统C规则，以C11草案核对。

### 1. 是的，截断后数值可能与原来不一致

用户的观察是对的。“截断”允许丢掉一部分信息，**只保留指定低位，不保证原数值不变**。

先类比十进制：假设只能保留最后两位，把 `4827` 截成 `27`，显然已经不是原来的数。二进制截断也是类似的操作，只不过保留的是最后几个二进制位；本例截到8位不是保留最后两位十进制数字。

一位十六进制对应4个二进制位。因此，截到8位就是保留最右边的两个十六进制数字：

```text
原来的16位：  0001 0010 | 1101 1011
十六进制：       1    2 |    D    B
                丢掉   |   保留
                       ↓
剩下的8位：              1101 1011
十六进制：                    DB
```

读图方法：竖线右边是低8位，保留；左边是高8位，丢掉。这里按通常写数的顺序排列，不是在画内存地址，也没有涉及大小端。

| 对象 | 位宽与解释方式 | 十进制值 |
|---|---|---:|
| 原来的 `0x12DB` | 16位无符号或16位补码，最高位都是0 | 4827 |
| 截断后的 `0xDB` | 8位无符号 | 219 |
| 截断后的 `0xDB` | 8位补码 | −37 |

原数可计算为 `1×4096 + 2×256 + 13×16 + 11 = 4827`，其中十六进制 D=13、B=11。也可以写成 **4827 = 18×256 + 219**：丢掉高位后，留下低8位对应的219。

所以讲义说的是“截断之后得到什么”，没有说 `0x12DB` 与 `0xDB` 相等。

截断也不一定改变数值。例如，`0x0025` 截到8位得到 `0x25`，两者都表示37，因为这次丢掉的只是前面的零，而且结果仍在8位无符号和补码范围内。不要把这个例子扩展成“只要丢掉零，任何解释下数值都不变”：目标解释也需要检查。

### 2. C是C语言；实现定义是由具体实现规定并写明规则

C是一种编程语言。下面就是C代码：

```c
int x = 4827;
signed char y = (signed char)x;
```

可以读成：“x保存整数4827；把它转换成 `signed char` 类型，再存到y里。”括号中的 `(signed char)` 表示要求进行类型转换。

在本课程环境中，`int` 是32位整数，`signed char` 是8位有符号整数。虽然名字里有 `char`，它也是整数类型，不是只能保存文字。其范围为 **−128～127**，装不下4827。

这时必须规定：“装不下怎么办？”

C语言标准是不同实现共同遵守的规则；编译器可以先理解为把C程序翻译成机器代码的软件，例如GCC。“实现”在这里指让C程序能够翻译、执行的具体系统，包括编译器及其目标环境，不是要求学习者自己实现一个函数。

**实现定义**的意思是：标准没有统一指定这一细节的具体结果，由具体实现作出规定，而且必须在文档里说明。

- 它不是每次运行随机决定。
- 在相同实现及相关条件下，应按照其文档中的规则理解。
- 换成另一种实现时，不能不查规则就保证结果相同。

它与“未定义行为”不同：实现定义要求实现说明它选择的规则；未定义行为则是C标准不再对该行为作出要求。这里讨论的是**超范围的整数类型转换**，不要与有符号加法溢出混为一谈。定义依据：[C11标准草案N1570，3.4.1、3.4.3](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)。

在教材所采用的传统C规则下，把整数转成装不下它的有符号整数类型，结果由实现规定；严格说，也允许引发一个由实现规定的信号。现阶段只需把这理解为“具体处理办法要查实现说明”，不用先学习信号机制。[N1570，6.3.1.3](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

GCC文档明确说明这类转换按目标类型的位宽取模，使结果落入该类型范围，且不引发信号。采用课程的8位 `signed char` 时，上面代码中的y得到 **−37**。[GCC整数转换说明](https://gcc.gnu.org/onlinedocs/gcc/Integers-implementation.html)

补充区分：若目标换成8位 `unsigned char`，范围是0～255，传统C标准本身就规定了超范围整数转换时的模256规则，因此4827转换后为219。这里“无符号”和“有符号”的语言保证不同。

### 3. x86补码截断模型是本课程机器题采用的计算规则

把这个词组拆开：

| 词语 | 在这里是什么意思 |
|---|---|
| x86 / x86-64 | CPU指令体系的名称，规定机器指令怎样工作；本课程主要采用x86-64 |
| 补码 | 用二进制位表示有符号整数的规则，可回看Q001 |
| 截断模型 | 这里使用的计算方法：只留下目标宽度的低位，再解释数值 |

“x86补码截断模型”是讲义对做题方法的描述，不是一条名叫这个名字的指令，也不是说所有C程序都由CPU自行决定转换规则。

对本例做两步：

```text
第一步：截到8位，保留低8位
0x12DB → 0xDB → 1101 1011

第二步：按题目指定的类型解释
无符号：128 + 64 + 16 + 8 + 2 + 1 = 219
补码： −128 + 64 + 16 + 8 + 2 + 1 = −37
```

**留下的位相同，解释方式不同，得到的数值就可能不同。** 截断时不要额外做一次“取反加一”；低8位已经确定，接下来是读取它表示的值。

这里写 `0xDB` 是在描述8位位模式。若直接在C源代码中写整数常量 `0xDB`，它在本课程环境中的类型是 `int`，数值是219；不能仅凭写了两个十六进制数字，就自动把它当成8位负数。

做题时：题目明确问8位机器截断，就“留低8位，再按目标类型读”；题目问C代码是否对所有实现都成立，就检查题目采用的C规则与具体实现，不能只凭某台机器上的结果作保证。

## Q003：“模”是什么意思，为什么这里要模256？

- 提问日期：2026-10-07（Asia/Shanghai）。
- 用户原始问题：“这个为什么要模啊 你之前也没说清 突然就冒出来一个模”
- 用户指定位置：复习第1讲，5.1「整数提升不是可忽略的小细节」。
- 截图原文：“如果再赋给 unsigned char，才按模 256 得到 4。”
- 出处：主讲义5.1，已与截图「codex-clipboard-2c018e3c-f629-4a58-b84d-81e1b5e2ea28.png」核对。知识点对应原课程第2讲的整数转换；教材、课件精确页码待核实。语言依据沿用Q002已核对的C11标准草案N1570，6.3.1.1（整数提升）与6.3.1.3（整数转换）。
- 解答性质：助手补充。采用课程x86-64/Linux环境，`unsigned char`为8位、`int`为32位。本例的取余解释针对非负整数260。

### 1. 先补上遗漏的定义：“模256”就是本例中的除以256取余数

原讲义没有先解释“模”，就直接使用它计算，这一步解释不充分。

前面的例子是 `250 + 10 = 260`。把260除以256：

```text
260 = 1 × 256 + 4
      ↑         ↑
      商        余数
```

因此，260模256得到4。**取的是余数，不是商，也不是四舍五入。** 这里的4不是需要额外背下来的特殊结果。

### 2. 为什么是256？因为目标是8位无符号整数

本课程环境中的 `unsigned char` 只有8位，每位可以是0或1，共有 **2⁸=256种位模式**，对应整数 **0～255**。

256是可表示数值的个数，也是最大值255加一。它不是最大可表示值；因此这里是模256，不是模255。

260超过了这个范围。C语言对整数转换到无符号整数类型规定了按“最大值加一”取模的处理规则；对8位 `unsigned char`，这个数就是256。[C11标准草案N1570，6.3.1.3](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

**位数有限说明原数装不下；具体为什么采用取模，是因为这里讨论的无符号转换规则这样规定。** 不要仅凭“装不下”就断定所有类型、所有操作都按取模处理。

### 3. 取模与“只保留低8位”有什么关系？

260写成二进制时，需要9位：

```text
260：        1 | 0000 0100
这一部分： 256 |    4
               ↓
只留低8位：    | 0000 0100 → 4
```

读图时看竖线：右侧恰好8位，保留；左侧放不下的高位丢掉。左边那个1的权重是256，右边剩下的位表示4，所以 **260 = 256 + 4**。

更一般地，高于低8位的那些位，其权重是256、512、1024等，都是256的倍数；低8位表示的非负数则在0～255之间。因此，对非负整数来说，**除以256取余数，恰好与只保留低8位得到相同的结果**。

| 转换前的非负整数 | 除以256，写成“商×256＋余数” | 转换成8位无符号后的值 |
|---:|---|---:|
| 255 | 0×256＋255 | 255 |
| 256 | 1×256＋0 | 0 |
| 260 | 1×256＋4 | 4 |
| 512 | 2×256＋0 | 0 |

从255再往上数，在这种8位无符号转换结果中就会回到0。这可以帮助理解“回绕”。取模不总是只减一次256：例如512需要减去两个256，余数才落在0～255内。

对于w位无符号整数，相应规则是模2ʷ；本题w=8，所以模256。先理解本题，不必急着背更大的数。

### 4. 先算出260，再在转换时得到4

```c
unsigned char a = 250;
unsigned char b = 10;

int sum = a + b;          // sum是260
unsigned char c = sum;   // 转换后c是4
```

`sum`可以理解为保存加法结果的变量；`c`则是接收转换结果的另一个变量。这段代码的过程是：

```text
a、b先提升成int
       ↓
按int做加法，得到260
       ↓
把260存入8位unsigned char
       ↓
按模256转换，得到4
```

本环境中，32位int能表示260，所以加法阶段没有发生溢出。如果只写 `int sum = a + b;`，结果就保留为260，没有随后那一步8位转换。

不是 `250 + 10` 算成了4，而是 **260转换成只能表示0～255的无符号类型后，得到4**。转换也不会把原来的sum改成4；这段代码执行后sum仍是260，c是4。

这里无需程序员额外写一条求余指令，赋值时的类型转换本身就按这个规则确定结果；具体生成哪些机器指令由编译器决定。

## Q004：图中的movl、寄存器与“小端还原”是什么意思？

- 出处：截图「codex-clipboard-36c6cba3-b329-499a-be5d-e3251a349506.png」，与主讲义图D1-F1及网页图表映射 `d1d2.json` 第一项核对。截图显示 `movl (%rdi), %eax`、从0x1000起读连续4字节、小端还原 `0x00000005` 以及执行后状态；上方寄存器和内存格子的完整初态由主讲义核对。

- 解答性质：助手补充。采用x86-64、AT&T汇编语法、小端、按字节编址及本例内存可正常读取的前提。

### 1. 先把整张图读成一句话

**rdi里存着地址0x1000；CPU从这个地址开始读出4个字节，把读到的整数5放进eax。**

原图提前使用了寄存器名、汇编指令和“小端”术语，在图旁解释不足。先理解这一次具体操作，再逐步学习更多指令。

### 2. 地址是格子的编号，内容是格子里存的东西

把内存想成一排有编号的小格子。每个格子存1字节，也就是8位。格子的编号叫地址；格子里实际存的位叫内容。

| 地址：格子的编号 | 内容：一个字节，按十六进制写 |
|---|---|
| `0x1000` | `05` |
| `0x1001` | `00` |
| `0x1002` | `00` |
| `0x1003` | `00` |

`0x` 是十六进制的前缀；内容栏省略了这个前缀。`05` 是一个字节的两位十六进制写法，二进制为 `0000 0101`；`00` 则是 `0000 0000`。

**0x1000是“去哪里找”，不是“找到的数是多少”。** 就像柜子的编号是100号，不代表里面一定有100件东西。

相邻格子的地址相差1，是因为一个地址对应一个字节。因此，从0x1000开始连续读4字节，要读的是0x1000、0x1001、0x1002、0x1003。

### 3. rdi与eax是CPU内部存储位置的名字

这些位置叫寄存器，可以先理解为CPU内部存放少量数据的小存储格。

- `%rdi`：本例中保存地址 `0x1000`，用于找到内存。
- `%eax`：本例中接收读出来的数据，容量为32位，即4字节。

名字前面的 `%` 是AT&T汇编语法标记寄存器的符号，**这里不是求余运算**。寄存器名字不是变量的数值，也不是内存地址。

rdi是64位寄存器，但**它保存地址的宽度，不决定这次读取多少字节**。本例读4字节，是由指令 `movl` 的宽度决定的。

### 4. 逐项拆开movl (%rdi), %eax

```text
movl       (%rdi)          ,       %eax
复制4字节   从rdi给出的地址读         放进eax
```

| 部分 | 在这条指令中的含义 |
|---|---|
| `mov` | 复制数据，不是搬走以后把原处清空 |
| 最后的 `l` | 小写字母L；指定32位，也就是4字节 |
| `(%rdi)` | 取rdi里的数作为地址，到该地址读取内存 |
| 逗号 | 分隔来源与目的；本套AT&T语法是左边来源、右边目的 |
| `%eax` | 用eax接收读到的数据 |

括号很关键：`%rdi` 直接表示寄存器里的数；`(%rdi)` 表示用那个数去找内存。本例rdi里的数是0x1000，读到的数据则表示5，二者不能混淆。

后缀 `l` 指4字节，不要把它和本课程C语言中8字节的 `long` 类型混为一谈。

### 5. 小端还原：为什么05 00 00 00表示5？

这4个字节共同表示一个32位整数。本课程的x86-64采用小端存放方式：**整数中权重最低的字节，放在最低地址。**

```text
按内存地址从小到大看：
地址      0x1000  0x1001  0x1002  0x1003
字节         05      00      00      00
数值权重      1     256    256²    256³
```

读图时把每个字节的数值乘以它的权重，再相加：

**5×1 + 0×256 + 0×256² + 0×256³ = 5。**

每字节有8位，所以按字节往更高位移动一格，权重乘以2⁸=256。这是位置权重，与Q003讲的“转换时取模”不是同一个操作。

我们平常写整数时，高位在左，低位在右。因此按照通常的写数顺序，这4个字节表示：

```text
00 00 00 05 → 0x00000005 → 十进制5
```

这里前面的零不会改变数值，写满8位十六进制数字是为了展示全部32位。

不要把按地址从小到大列出的 `05 00 00 00` 直接拼成通常书写的整数 `0x05000000`。两行采用的是不同排列顺序。

**“还原”只是按存放规则读出数值，不是把内存字节实际搬动或重新排列。** 每个字节内部的0和1也没有反转。

### 6. 执行后改变了什么？

| 位置 | 执行前 | 执行后 |
|---|---|---|
| `%rdi` | 地址0x1000 | 仍是地址0x1000 |
| `%eax` | 原图用问号表示本例未给定初值 | 5，即0x00000005 |
| 内存0x1000～0x1003 | 05、00、00、00 | 仍是05、00、00、00 |

它完成的是一次读取并复制。就像照着柜子里的纸条，把数字抄到手边：柜号没变，原纸条也没变。

这条指令不会自动让rdi增加4。图里的 `%eax = 5` 是说明执行结果，不是一条额外的C语句或汇编指令。

留到第8节再展开的一点：eax是rax的低32位；x86-64中写eax还会把rax的高32位清零，因此本例执行后完整rax也是5。这不影响本图“地址与内存内容没有改变”的结论。

## Q005：掩码是什么，四种掩码表达式分别怎样工作？

- 提问日期：2026-10-07（Asia/Shanghai）。
- 用户原始问题：“解释一下如图的几个所谓的掩码 以及掩码是什么”
- 用户指定位置：复习第1讲，第3节「位运算和逻辑运算：长得像，处理对象不同」末段。
- 出处：截图「codex-clipboard-2fe9698e-e596-479f-9641-c56a8af5209c.png」，与主讲义中的 `x & 0xFFu`、`x & ~0xFu`、`x | (1u << k)`、`x ^ (1u << k)` 四种表达式核对。对应原课程第2讲，教材位级运算与移位相关小节2.1.7、2.1.9；教材印刷页码、PDF页序及课件精确页序待核实。
- 解答性质：助手补充。采用课程x86-64/Linux环境，x为32位 `unsigned int`，k取整数0～31。低8位示意图只为便于阅读，不代表把C运算改成8位；图中文字的二进制位串不是可直接照抄的C常量写法。

### 1. 先看一个掩码实际怎样工作

假设有一串数据 `1010 1101`，只想保留最右边4位，就配上一串 `0000 1111`，做按位与：

```text
原数据：  1010 1101
掩码：    0000 1111
做 & ：   0000 1101
```

读图时把上下两行的对应位对齐，一列一列计算。按位与 `&` 要求同一列的两位都是1，结果才是1。

- **某一位 & 1：保留原位。** 因为 `0 & 1 = 0`，`1 & 1 = 1`。
- **某一位 & 0：清零。** 无论原位是0还是1，结果都是0。

所以掩码 `0000 1111` 相当于告诉这次与运算：“前面4位清零，后面4位原样留下。”

**掩码（mask）就是一串配合位运算、控制哪些位保留或改变的0和1。** 它本身也是普通的整数，不是一种特殊数据类型；“掩码”描述的是这个数在运算中的用途。结果还取决于与它配合的运算符。

### 2. 先认清四种表达式里的符号

| 写法 | 含义 |
|---|---|
| `0x` | 后面的数按十六进制书写 |
| `F` | 十六进制的一位，值为15，对应二进制1111 |
| 数字末尾的 `u` | 指定无符号整数常量；不是额外的数据位，也不是单位 |
| `~` | 逐位取反：0变1，1变0 |
| `<< k` | 左移k位，右侧空位补0 |
| `&`、`\|`、`^` | 按位与、按位或、按位异或；这里的 `^` 不是乘方 |

在本课程环境中，`0xFFu`、`0xFu`、`1u` 都是32位 `unsigned int` 常量。没有写出的高位是0，不能因只写了一个或两个十六进制数字，就把它们当成4位或8位类型。

位编号从最右边的第0位开始。下面只展示低8位的编号；完整32位的编号为31～0：

```text
从左到右：  高位                 低位
位编号：     7  6  5  4  3  2  1  0
```

因此，第3位是从右往左数的第4个位置。

### 3. x & 0xFFu：保留低8位，高24位清零

两个F对应8个1。完整32位掩码是：

```text
0xFFu：00000000 00000000 00000000 11111111
       高24位：0                  低8位：1
```

与1保留，与0清零，因此只有低8位原样留下。例如：

```text
x：       0x1234ABCD
掩码：    0x000000FF
做 & ：   0x000000CD
```

这句话的“保留低8位”并不是把结果类型变成8位。结果仍然是32位无符号整数，只是高24位都变成了0。

### 4. x & ~0xFu：低4位清零，其余位保留

先构造掩码。一个F对应4个1；`~` 再把全部32位取反：

```text
 0xFu：00000000 00000000 00000000 00001111
~0xFu：11111111 11111111 11111111 11110000
```

第二行就是 `0xFFFFFFF0`。让x与它做 `&`：低4位遇到0，清零；其他位遇到1，保留。例如：

```text
x：       0x1234ABCD
掩码：    0xFFFFFFF0
做 & ：   0x1234ABC0
```

这里 `~` 取反的是掩码 `0xFu`，不是x。高位的F也是必要的：如果误把掩码写成 `0xF0u`，它的高24位都是0，与运算会把x的高24位也清零。

### 5. x | (1u << k)：把第k位设为1

`1u << k` 把数字1中唯一的二进制1向左移动k位，得到“只有第k位为1”的掩码。

例如k=3，只展示低8位：

```text
1u：       0000 0001
1u << 3：  0000 1000
```

这个掩码完整写出是 `0x00000008`。然后做按位或 `|`：

- 与1做或，结果一定为1。
- 与0做或，原位不变。

```text
x的低8位： 0101 0010
掩码：     0000 1000
做 | ：    0101 1010
```

只有第3位被设为1；高24位因对应的掩码位都是0，也保持不变。如果第3位原本就是1，结果仍然是1，不会变回0。

### 6. x ^ (1u << k)：翻转第k位

掩码与上一种相同，改变的是运算符。异或 `^` 的规则是：对应的两位不同，结果为1；相同，结果为0。

因此：

- 与1异或就翻转：`0 ^ 1 = 1`，`1 ^ 1 = 0`。
- 与0异或就保留：`0 ^ 0 = 0`，`1 ^ 0 = 1`。

仍取k=3，这次用第3位已经为1的数作例子：

```text
x的低8位： 0101 1010
掩码：     0000 1000
做 ^ ：    0101 0010
```

第3位从1变成0，其他位不变。如果它原本为0，就会变成1。因此，**置1是“不管原来如何，最后为1”；翻转是“把原来那一位反过来”。**

### 7. 掩码里的1是什么意思，要结合运算看

| 运算 | 掩码这一位为0 | 掩码这一位为1 |
|---|---|---|
| `x & 掩码` | 清零 | 保留 |
| `x \| 掩码` | 保留 | 设为1 |
| `x ^ 掩码` | 保留 | 翻转 |

不能只背“掩码中的1表示保留”。这是与运算的规则；换成或、异或，就分别变成置1、翻转。

这些表达式只计算出一个结果，不会自动改写x。要改变x本身，应赋值，例如：

```c
x = x & 0xFFu;        // 高24位清零，保留低8位
x = x | (1u << k);    // 把第k位设为1
```

上面每行说明其各自效果，不要求把它们连续执行。也可以用 `x &= 0xFFu;`、`x |= (1u << k);` 这样的复合赋值写法；初学时先读懂完整写法即可。

本例的k必须是0～31；32位类型只有第0～31位，C中负移位量或大于等于32的移位量不能按这里的方法使用。使用 `1u` 是为了明确在无符号类型上移位，包括构造第31位的掩码。

## Q006：addb是什么，和C里的加法有什么区别？

- 提问日期：2026-10-07（Asia/Shanghai）。
- 用户原始问题：“addb是什么”
- 用户指定位置：复习第1讲，5.1「整数提升不是可忽略的小细节」。
- 出处：主讲义5.1末段中的 `addb`，并与本讲8.2的指令宽度及源、目的顺序核对。本知识点对应原课程第4讲的整数算术指令；教材、课件精确页码待核实。
- 解答性质：助手补充。采用x86-64、AT&T汇编语法；C对照采用课程Linux环境中的32位int与8位unsigned char。

### 1. addb就是8位加法指令

**`addb` 表示“做一次8位（1字节）加法”。**

- `add`：加法。
- `b`：byte，即字节；说明这次处理的数据宽度为1字节，也就是8位。

它是汇编指令的写法，不是C语言的函数或变量名。此前的 `movl` 也采用“操作名加宽度后缀”的形式：mov表示复制，l表示32位；这里add表示加法，b表示8位。

### 2. 看一条完整的指令

```asm
addb $10, %al
```

意思是：**把10加到al原来的值上，结果写回al。**

| 部分 | 含义 |
|---|---|
| `addb` | 做8位加法 |
| `$10` | 直接使用常数10；`$` 是AT&T语法中立即数的标记 |
| `%al` | 8位寄存器名称，更准确地说是rax的最低8位；不是之前32位的eax |
| 左边来源、右边目的 | 目的的新值由“目的旧值＋来源”得到 |

这条指令没有给出内存操作数，直接读取al的原值并写回al。

### 3. 如果al原来按无符号读是250，会发生什么？

```text
原来：250 =   1111 1010
加上： 10 =   0000 1010
           ───────────
数学结果：  1 0000 0100 = 260
              ↓
只保存低8位： 0000 0100 = 4
```

读图时注意：数学结果需要9位，但al只有8位，所以只写入最右边8位。执行后al为 `0000 0100`，按无符号读是4。与Q003中的算术联系是260模256等于4。

超出的进位不写进al；addb还会更新进位等标志位，后面学习条件码时再展开。这里不是说进位对CPU的其他状态完全没有影响。

al本身不带C语言的有符号或无符号类型。这里明确按无符号数读初态，才把 `1111 1010` 称作250；指令处理的是这些位。写al只改变rax的低8位，保留rax其他位。

### 4. 为什么整数提升这一节提到它？

讲义要区分两种层次：

| 情况 | 按多宽计算 | 250＋10的结果 |
|---|---|---|
| C中两个unsigned char相加 | 本环境先提升成32位int | 先得到260；若再存入unsigned char，才转换成4 |
| 汇编明确写addb | 直接进行8位加法 | 目标只保存低8位，即4 |

**C里的变量原来是8位，不等于加法也按8位做；汇编的addb已经明确指定8位。**

这是语言规则与给定机器指令的对照，不是在保证某段C代码一定编译出哪条汇编指令；编译器可以在保持程序所需行为的前提下优化。

## Q007：无符号类型等级较低时，究竟转成什么？

- 提问日期：2026-10-07（Asia/Shanghai）。
- 用户原始问题：“一、有符号、无符号问题中，当无符号类型的等级要低于有符号类型等级的话，应该怎么办？你说的不是特别清楚”
- 用户指定位置：复习第1讲，D1-E2；相关规则在5.2。
- 出处：主讲义5.2及D1-E2，原课程第2讲的整数类型转换。教材及课件精确页码待核实；语言规则核对C11标准草案N1570，6.3.1.1和6.3.1.8。
- 解答性质：助手补充；采用课程Linux x86-64的LP64环境，int为32位，long与long long为64位，不套用其他平台位宽。

### 1. 等级低的无符号类型，不一定让整个计算采用无符号

先做整数提升，再比较剩下的操作数类型。如果无符号类型的等级低于有符号类型，就再问：**这个有符号类型能不能表示无符号类型的全部取值？**

| 有符号类型能否表示无符号类型的全部值？ | 统一后的操作数类型 |
|---|---|
| 能 | 原来的高等级有符号类型 |
| 不能 | 原来的高等级有符号类型所对应的无符号类型 |

这个判断不能省略，也不能直接说“等级高的一定赢”。

### 2. 能装下的例子：long与unsigned int

本课程环境中：

```text
unsigned int：32位，范围0 ～ 2³²−1
long：        64位，范围−2⁶³ ～ 2⁶³−1
```

long的等级更高，而且能表示unsigned int的全部值。因此unsigned int操作数转为long，原来的long操作数保持long。

```c
-2L < 1U
```

这里左边是long类型的−2，右边是unsigned int类型的1。比较前双方统一为long，所以是在比较−2与1，结果为真。

### 3. 装不下的例子：long long与unsigned long

常见整数类型的等级顺序为：

```text
signed char < short < int < long < long long
```

每种有符号类型与它对应的无符号类型等级相同。例如int与unsigned int同级，long与unsigned long同级。

**等级不等于位宽。** 本环境中long和long long都是64位，但long long的等级仍高于long，也高于unsigned long。

```text
unsigned long的最大值：2⁶⁴−1
long long的最大值：    2⁶³−1
```

long long无法容纳unsigned long的全部取值。因此公共类型选long long对应的无符号类型，即 **unsigned long long**：

```text
long long     → unsigned long long
unsigned long → unsigned long long
```

不是回到低等级的unsigned long，也不是把“对应无符号类型”理解为随便挑一个unsigned。

### 4. 看的是类型的全部范围，不是变量现在的数值

```c
long long a = -2;
unsigned long b = 1;
int result = a < b;
```

即使b此刻只存1，规则仍然检查long long能否表示unsigned long的**全部**范围。答案是否定的，所以比较操作数统一到unsigned long long；a的−2转换后为2⁶⁴−2，与1比较，结果为假，result为0。

这里的“公共类型”说的是两个比较操作数的类型；C中 `<` 产生的比较结果本身是int类型的0或1。

完整的混合有符号/无符号判断，可以这样走：

```text
先完成整数提升
      ↓
无符号类型等级 ≥ 有符号类型等级？
  是 → 转成这个无符号类型
  否 → 有符号类型能容纳无符号类型的全部值？
          能 → 转成这个有符号类型
          不能 → 转成这个有符号类型对应的无符号类型
```

适用于本题的比较及采用通常算术转换的整数运算，不要把该流程机械套到移位等使用不同规则的运算。

规则依据：[C11标准草案N1570，6.3.1.1、6.3.1.8](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)。上面的数值与代码是助手按课程环境编写的示例。

## Q008：整数常量只有u后缀，怎样判断具体类型？

- 提问日期：2026-10-07（Asia/Shanghai）。
- 用户原始问题：“第二个问题是，如果一个数字后面只有一个 u，那肯定是 unsigned 类型，但具体是 unsigned int、char 还是 long，该怎么判断”
- 用户指定位置：复习第1讲，D1-E2；相关概念在5.2的常量后缀说明。
- 出处：主讲义5.2与D1-E2的 `unsigned u = (unsigned)x;`、`u + 40U`。教材、课件精确页码待核实；常量规则核对C11标准草案N1570，6.4.4.1，类型说明见6.7.2。
- 解答性质：助手补充；按课程Linux x86-64环境，unsigned int为32位，unsigned long和unsigned long long为64位。

### 1. 仅有u或U后缀，依次选第一个装得下的类型

这里讨论写在C代码中的整数常量，例如 `40U`、`255u`。只有u或U后缀时，候选顺序为：

```text
unsigned int
     ↓ 装不下再看
unsigned long
     ↓ 装不下再看
unsigned long long
```

**候选列表中没有unsigned char，也没有unsigned short。** 即使数值只有1，也不会因为它很小而自动选成char。

u与U效果相同。仅有U的这份候选顺序，对十进制、八进制和十六进制整数常量相同；其他后缀或没有后缀时要查各自的候选列表。

### 2. 按课程位宽判断几个例子

32位unsigned int能表示0～4294967295，即0～2³²−1；64位unsigned long能表示0～2⁶⁴−1。

| 常量 | 在本课程环境中的类型 | 判断理由 |
|---|---|---|
| `1u`、`40U`、`255u` | unsigned int | 第一种候选就装得下 |
| `4294967295u` | unsigned int | 恰好等于2³²−1 |
| `4294967296u` | unsigned long | 超出32位unsigned int，64位unsigned long能表示 |
| `0xFFFFFFFFu` | unsigned int | 值为2³²−1 |
| `0x100000000u` | unsigned long | 值为2³² |

本环境的unsigned long与unsigned long long同为64位、范围相同。对仅U后缀且能由这些标准类型表示的整数，unsigned long装得下就先选它，不会因为unsigned long long等级更高而越过前者。

列表中所有类型都装不下时，不能把它当作普通的“自动截断常量”；这涉及实现支持的扩展类型或诊断，不是本例的赋值截断规则。

### 3. UL、ULL与单独U有什么区别？

| 后缀 | 标准候选类型顺序 | 小数值例子 |
|---|---|---|
| `U` | unsigned int → unsigned long → unsigned long long | `1U`是unsigned int |
| `UL` | unsigned long → unsigned long long | `1UL`是unsigned long |
| `ULL` | unsigned long long | `1ULL`是unsigned long long |

推荐用大写L，避免小写l与数字1混淆。这些是整数后缀规则；无需为本题引入浮点常量的后缀。

规则依据：[C11标准草案N1570，6.4.4.1](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)。具体类型选择还依赖平台范围，上表实例采用本课程环境。

### 4. 常量的类型，不等于接收它的变量的类型

```c
unsigned char c = 1u;
```

- 右边的常量 `1u` 自身是unsigned int。
- 左边变量c的类型是unsigned char，由声明决定。
- 赋值时，把右边的值转换成左边的类型；本例数值仍为1。

不是因为c是char，右边的1u就自动变成char类型的常量。

### 5. 联系D1-E2：unsigned简写、变量名u和40U

```c
unsigned u = (unsigned)x;
unsigned v = u + 40U;
```

这里有三个容易混淆的东西：

| 写法 | 含义 |
|---|---|
| 声明或强制转换中单独写 `unsigned` | unsigned int的简写 |
| 变量名 `u` | 只是名字，本身不决定类型 |
| 常量 `40U` | 带U后缀的整数常量，因40能被unsigned int表示，所以选unsigned int |

因此例题中的变量u、v和常量40U都是unsigned int。若写成 `int u;`，即使变量名还叫u，它的类型也是int。

## Q009：有符号结果超出范围时，也能直接取模吗？

- 提问日期：2026-10-07（Asia/Shanghai）。
- 用户指定位置：复习第1讲，D1-E2；关联4.2的转换、5.1的整数提升及6.1的溢出。
- 用户原始问题：

> 然后还有个小问题，我想向你确认一下
>
> 1. 负数转 unsigned 是对对应的 2 的欧米伽次方进行取模
> 2. 正数转的话就直接过去
> 3. 如果这个值大于 unsigned 这个值的话，就还是取模
> 4. 无符号结果要保留模 2 的欧米伽次方的值
>
> 那如果说有符号结果的话，应该怎么处理？如果有负号结果，然后也超过了这个 2 的欧米伽次方

- 出处：主讲义D1-E2及6.1；原课程第2讲的整数转换和运算。教材及课件精确页码待核实；C语义沿用已核对的C11标准草案N1570，6.3.1.3、6.5。
- 解答性质：助手补充。采用本课程x86-64/Linux环境、32位int及补码位模型；8位机器示例会单独明示，不当成C默认的运算宽度。

### 1. 先确认无符号的四点，并明确w是什么

讲义里的w表示位数，不是这里必须使用的希腊字母欧米伽。8位时w=8，2ʷ=256。

**整数转换到w位无符号类型，统一按模2ʷ处理，结果落在0～2ʷ−1。**

- 原数在这个范围内，转换后数值不变；所以“正数直接过去”要加上“目标类型装得下”的条件，零也一样。
- 超过最大值2ʷ−1的正数要取模；等于2ʷ时也已经超范围。
- 负数也取模，取这个范围里的非负结果。
- 无符号加减乘按实际运算类型的位宽取模；如果先发生整数提升，要按提升后的类型判断，不能只看原变量多宽。

8位无符号转换的例子：

| 数学整数 | 转换后的值 | 计算 |
|---:|---:|---|
| 24 | 24 | 本来就在0～255中 |
| 256 | 0 | 256=1×256＋0 |
| 260 | 4 | 260=1×256＋4 |
| −24 | 232 | −24=−1×256＋232 |

这里说的负数“取模”要得到0～255里的数。不要直接照搬C的负数 `%` 运算：C中 `-24 % 256` 得到−24，不能把它当作转换到8位无符号类型的232。

### 2. 有符号数要检查另一条范围线

| w位表示方式 | 范围 | w=8时 |
|---|---|---|
| 无符号 | 0～2ʷ−1 | 0～255 |
| 有符号补码 | −2^(w−1)～2^(w−1)−1 | −128～127 |

**有符号结果不是等到超过2ʷ才有问题。** 8位时，140虽然小于256，却已经大于127；−140则已经小于−128。

“负数超过2ʷ”如果是指负数的绝对值超过2ʷ，例如−300的绝对值超过256，它当然也超出8位补码范围。但要更早检查−128这个下界，不能等到−256才检查。

是否超范围与该怎样处理，还要看题目属于下面哪一种情境。

### 3. 明确要求w位补码机器运算：保留位，再按补码读

对于题目规定保留低w位的机器加减乘模型，先计算数学结果，再做两步：

1. 模2ʷ，得到0～2ʷ−1的值，确定保留下来的w位模式。
2. 按补码读：若该值小于2^(w−1)，原样读；否则减去2ʷ。

8位时，这两步就是先模256，再判断是否大于等于128。

**正方向超范围：明确做8位机器加法120＋20。**

```text
数学结果：120 + 20 = 140
低8位：  1000 1100
最高位为1，按补码读：140 − 256 = −116
```

数学结果140超出了−128～127，所以这里发生了有符号溢出。−116是机器保留位的补码解释，不是数学加法的正确结果。

**负方向超范围：明确做8位机器加法−120＋(−20)。**

```text
数学结果：−120 + (−20) = −140
−140 = −1×256 + 116
低8位：0111 0100
最高位为0，按补码读：+116
```

这次同样发生有符号溢出，因为数学结果−140小于−128。

**绝对值连256都超过的负结果：例如−20×15＝−300，题目要求只保留乘积低8位。**

```text
−300 = −2×256 + 212
低8位：1101 0100
最高位为1，按补码读：212 − 256 = −44
```

不论越界多少，保留低8位的模型仍按这个过程处理；不是遇到负数就只加一次256。

### 4. C里的有符号算术：超出实际运算类型范围是未定义行为

C中有符号加减乘的数学结果如果超出了实际运算类型的范围，属于未定义行为，不能把它普遍解释成“自动取模回绕”。

课程中int是32位，范围为−2147483648～2147483647：

```c
int x = 2147483647;
int y = x + 1;  // 有符号int溢出：未定义行为
```

不能保证y等于−2147483648。C标准不再对这一溢出行为作出要求，不能因为某次机器运行留下了某个位模式，就把它当成语言保证。

反过来，普通C表达式 `120 + 20` 是按int计算，140在32位int范围内，所以结果就是140，没有有符号溢出。即使原变量是signed char，本环境中加法也会先做整数提升；不要把前面明确指定的8位机器加法直接套过来。

### 5. 已有整数转换到有符号窄类型：另看转换规则

```c
int x = 140;
signed char y = (signed char)x;
```

这里140正常存放在int里，没有发生int加法溢出。问题是随后把140转换到只能表示−128～127的signed char。

按教材采用的传统C规则，超范围的整数到有符号类型转换，结果由实现规定，或引发实现规定的信号。本课程通常采用的实现留下低8位，并将其按补码读成−116。这和上一节“C有符号算术溢出是未定义行为”不是同一条规则；没有超出目标范围时则保持原值。

规则依据：[C11标准草案N1570，6.3.1.3、6.5](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)。具体实现例子可回看 [Q002：截断与实现定义](第一讲后补充讲义.md)。

### 6. 做题先认清自己在哪一层

| 题目在问什么 | 如何处理 |
|---|---|
| 整数转成w位无符号类型 | 模2ʷ，得到0～2ʷ−1的结果 |
| 无符号加减乘 | 按实际运算类型位宽取模；先考虑提升和公共类型 |
| 明确指定保留低w位的补码机器运算 | 保留低w位，再按补码解释，并判断有符号溢出 |
| C有符号加减乘 | 在实际运算类型范围内正常计算；越界是未定义行为 |
| 整数转成有符号窄类型 | 未越界保留原值；越界按教材采用的传统C实现定义规则处理 |

是否有负号，不能单独决定用哪一行；要先看题目说的是类型转换、C算术还是机器指令。

### 追问1：有符号加法的结果超过2^(w−1)−1，具体怎么办？

- 追问日期：2026-10-07（Asia/Shanghai）。
- 用户原话：“那如果说在加法运算中有符号数的结果，超了 2 的 w - 1次方 - 1的话应该怎么办”
- 出处：本对话对Q009的后续追问；关联主讲义6.1。以下为助手补充。

**如果w就是实际做有符号加法的位宽，那么数学结果超过2^(w−1)−1，就发生有符号溢出。** 等于这个最大值仍然合法，超过才是溢出。

**机器题：明确要求两个w位补码数相加并保留低w位时，正方向溢出的机器结果按补码解释为“数学和减去2ʷ”。**

例如8位补码最大值为127：

```text
120 + 20 = 140，超过127
保留的8位：1000 1100
按补码解释：140 − 256 = −116
```

所以作答应包含两点：“发生有符号溢出；8位机器结果按补码解释为−116。”这里减的是2ʷ，不是2^(w−1)。

为什么这次减一次就够？两个合法的w位有符号数，最大数学和是 `2×(2^(w−1)−1)=2ʷ−2`，不可能在这一次两数相加中达到或超过2ʷ。正溢出时，保留下来的位最高位为1，把它按补码读正好需要减去2ʷ。这一简式不能直接泛化为任意多项数学和或任意乘积只减一次就够。

**C题：如果提升和公共类型转换后实际仍是w位有符号加法，超过该类型最大值，则是未定义行为。** 不能保证回绕成“数学和−2ʷ”。

特别注意下面的代码：

```c
signed char a = 120, b = 20;
int c = a + b;
```

在本课程环境中，a、b先提升成32位int；140在int范围内，所以c正常得到140，没有加法溢出。不能把原变量的8位当成实际加法的位宽。

这一问先记住：**明确的补码机器题，标明溢出并计算回绕结果；C有符号加法题，实际运算类型越界则答未定义行为。** 本次是澄清原解答，不修改先前例题结果。

### 追问2：数学结果达到2³²＋16，还能按有符号数处理吗？

- 追问日期：2026-10-07（Asia/Shanghai）。
- 用户原话：“那比如说计算出来的结果是 2 的 32 次方加 16，也就是说已经超过了 32 位 int，然后这还是有符号数，这可怎么办”
- 出处：本对话对Q009追问1的继续追问，并关联D1-E2第二步。以下为助手补充。

**先区分“数学上推算得到2³²＋16”和“32位int已经合法存下这个值”。后者不可能。** 32位有符号int的最大值是2³¹−1，早在到达2³²之前就已越界。

**如果题目明确按机器模型只保留低32位：**

```text
数学结果：2³² + 16
取模2³²：16
低32位： 0x00000010
最高位是0，按32位补码读仍为正数16
```

不能再对16减一次2³²。只有保留的32位最高位为1，即其无符号值大于等于2³¹时，才需要减2³²来得到补码值。

因此，任意较大数学结果保留低32位后，不一定呈现负数；最终的正负取决于保留下来的位。不能仅看最终结果为正，就倒推整个运算过程没有发生溢出。

**如果讨论C里的32位有符号int算术：** 数学结果超出int范围就没有合法的int结果，属于有符号溢出，行为未定义，不能保证得到16。C不会根据即将产生的大结果，自动把int运算升级成long；多步表达式还必须逐步检查，不能只检查最后的数学总结果。

**如果实际运算类型是64位有符号类型，则另当别论。** 2³²＋16没有超过64位补码的最大值2⁶³−1。例如本课程Linux x86-64环境中：

```c
long x = 4294967296L + 16L;
```

两边本来就是64位long，正常计算并保存4294967312，没有溢出，也不需要截断成16。关键是运算前的类型已经足够宽，而不是算完溢出后再补救。

**上一条“两个w位补码数相加，正溢出就减2ʷ”的前提不能省略。** 两个合法32位int的最大数学和为：

```text
(2³¹−1) + (2³¹−1) = 2³²−2
```

所以两个合法32位int相加，本来就不可能产生2³²＋16这么大的数学和。如果是更宽类型、多项运算或乘法，必须按具体情境处理，不能直接套两数相加的简式。

**回到D1-E2：那里的2³²＋16来自无符号加法。**

```c
unsigned v = u + 40U;
```

u已经是unsigned int，40U也是unsigned int。`(2³²−24)+40=2³²+16` 是为了推导而写出的数学和；这次C无符号加法按模2³²定义，v正常得到16。虽然更早的x是负的int，但这一步已经完成向unsigned的转换，不再是有符号int加法。

本次补充明确了32位机器截断、C有符号运算以及64位有符号正常计算的区别；原例题和上一条带前提的两数加法公式不变。

### 追问3：数学结果为−2³²−6，只保留32位时怎么办？

- 追问日期：2026-10-07（Asia/Shanghai）。
- 用户原话：“那如果是算出来的有符号数是负的，比如负的 2 的 32 次方减 6，这样也是越界了，怎么处理”
- 出处：本对话对Q009追问2的继续追问，关联主讲义6.1。按用户语句将数学结果理解为 `−(2³²)−6`。以下为助手补充。

**如果明确只保留低32位，然后按32位补码读，结果是−6。** 先确定保留下来的位，再解释正负，不需要为正结果和负结果另背两套任意回绕规则。

**第一步：对2³²取模，余数要落在0～2³²−1。**

```text
−2³²−6 = (−2)×2³² + (2³²−6)
                         ↑
                  所选的非负余数
```

所以保留位对应的无符号值为2³²−6，即4294967290；32位模式为 `0xFFFFFFFA`。

原数只加一次2³²会得到−6，但−6还不是0～2³²−1范围内的非负余数；再加一次2³²才得到2³²−6。这里是数学取模，不是把负数直接交给C的 `%` 运算符；后者的负余数规则见本条第1节。

**第二步：将同一串位按32位补码解释。**

`0xFFFFFFFA` 的最高位为1，所以用它的无符号值减2³²：

```text
(2³²−6) − 2³² = −6
```

完整过程：

```text
数学结果：−2³²−6
     ↓ 取模2³²，确定低32位
无符号读法：2³²−6，即0xFFFFFFFA
     ↓ 同一串位按补码读
有符号读法：−6
```

最终的−6与中途“加一次2³²”得到的−6碰巧相同；分成两步，是为了始终明确哪个数是在描述位模式、哪个数是补码解释。也可以从原数加减2³²的倍数，直到得到补码范围内的同余值，但不能把“加一次就够”当作通用规则。

**仍要区别实际计算情境：**

| 情境 | 本例怎样处理 |
|---|---|
| 题目明确给定数学结果并要求保留低32位、按补码读 | 机器截断结果为−6 |
| C中实际32位有符号int算术的数学结果越界 | 有符号溢出，行为未定义，不能保证−6 |
| 实际按64位有符号类型计算，且各步合法 | 原数−4294967302在范围内，可正常保留，不需截断 |

两个合法32位int相加，数学上最小为 `−2³¹ + (−2³¹) = −2³²`，所以仅靠一次这样的两数相加，也不可能得到更小的−2³²−6。若是多步运算、乘法或更宽类型，必须按各步实际类型和题目条件分析。

本次补充负方向的大数例子，与追问2的正方向例子采用同一规则：**保留低位的机器模型先取模确定位，再依据最高位作补码解释；不能据此给C有符号溢出承诺回绕结果。**

## Q010：移位表中是有符号还是无符号？补码与有符号有什么区别？

- 用户原始问题：“如图的这三个例子中，都是有符号数还是无符号数 补码和有符号数的区别是什么”

- 出处：截图「codex-clipboard-a3d543f9-6c62-4c05-8e2d-d9254b5292d1.png」，与主讲义6.2三行移位表核对。截图未包含的初始模式 `1101 1011` 已从表前正文核实。对应原课程第2讲，教材2.1.9（移位）与2.2.3（补码编码）；精确教材印刷页码、PDF页序及课件页序待核实。
- 解答性质：助手补充；采用本课程x86-64补码表示。本表是固定8位机器位模型，不是8位C表达式计算。

### 1. 三行先讲的是位怎么移动，没有统一指定一种C整数类型

原始位模式为 `1101 1011`。三行分别从这个初态出发，各自移动2位，不是把上一次结果接着往下移。

```text
同一串8位：1101 1011
按无符号读：128+64+16+8+2+1 = 219
按补码读： −128+64+16+8+2+1 = −37
```

**位串本身没有“天生的正负”。** 同一串位采用哪种数值解释，要由类型或题目约定决定。机器寄存器也不会为这串位额外保存一个C类型标签。

先按操作规则移动位，再按题目需要解释数值：

| 操作 | 得到的8位模式 | 按8位无符号读 | 按8位补码读 |
|---|---|---:|---:|
| 左移2位 | `0110 1100` | 108 | 108 |
| 逻辑右移2位 | `0011 0110` | 54 | 54 |
| 算术右移2位 | `1111 0110` | 246 | −10 |

读表时，先看第二列的位，再选择第三或第四列的读法。最后两列是在解释同一结果，不是进行了两次不同的移位。

### 2. 三种移位各自怎样理解？

**左移：右侧补0，超出左侧的位丢弃。**

```text
初态：          1101 1011
向左移2位：  11 | 0110 1100
              丢掉   保留8位
```

不论原数按无符号219还是补码−37理解，位操作都得到 `0110 1100`，即108。无符号解释下，219×4=876，保留低8位得到108；补码解释下，−37×4=−148，超出8位范围，保留低8位也得到108。不能说该左移始终保持原符号，或在有符号解释下仍得到正确的数学乘积。

**逻辑右移：左侧补0。**

```text
初态：     1101 1011
右移2位： 0011 0110  | 11
             保留8位   丢掉
```

通常用于无符号数的右移。把初态按219理解时，219÷4=54.75，向下取整得到54，正好对应 `0011 0110`。

如果把初态理解成−37，机器仍能对同一串位执行逻辑右移，结果也是54；但这就不是保持补码负数含义的右移。

**算术右移：左侧复制原最高位。**

```text
初态：     1101 1011，原最高位为1
右移2位： 1111 0110  | 11
           ↑↑          丢掉
         左边补两个1
```

通常用于补码有符号数。把初态按−37理解时，−37÷4=−9.25，向下取整得到−10，对应 `1111 0110`。

如果把这次结果按无符号数读，就会得到246，但246不是219÷4的结果。这说明“通常用途”依赖所需的数值含义，并不改变机器如何移动这些位。

初态最高位为0时，算术右移也补0，与同宽同移位量的逻辑右移产生相同位模式。

### 3. 有符号说的是数值类型，补码说的是编码方法

**有符号整数类型**允许表示负数、零和正数，例如 `signed char`、`int`。它不意味着变量现在一定是负数：`int x = 5;` 中x仍是有符号类型，只不过当前值为正。

**补码**是一种把这些整数表示成二进制位的方法。本课程x86-64有符号整数采用这种方法。

可以这样区分：

> “有符号”说这种类型允许表示正负整数；“补码”说这些整数怎样用0和1编码。

有符号整数在其他表示方案中也可以采用原码、反码等编码，因此概念上二者不是同义词；本课程的机器环境已经选定补码，不用在每道题里重新选择编码方式。

补码也表示正数和零，不是只有负数才有补码：

| 8位补码 | 表示的整数 |
|---|---:|
| `0000 0101` | ＋5 |
| `0000 0000` | 0 |
| `1111 1011` | −5 |

本课程中，“按8位补码读”可以理解为“按采用补码表示的8位有符号整数读”；相应地，“按8位无符号读”采用0～255的数值解释。

### 4. 为什么说算术右移复制的是符号位？

在补码解释下，原最高位为0意味着数值非负，为1意味着负数。算术右移复制它，使非负数在左侧补0、负数在左侧补1，从而保持这种符号解释。

如果只按无符号数看，最高位只是一个有正权重的位，不叫它负号。算术右移的物理操作仍然是“复制最高位”；只有联系补码解释时，才称为“符号扩展式的右移”。

### 5. 这张表不是三段C代码

图中直接规定8位和具体移动方式，是机器位操作示意。若真的给出C表达式，还要先看整数提升、操作数类型及语言规则：

- 本课程环境中的unsigned char参与移位前会提升成int，不能机械照搬“变量原来8位，所以只移8位”。
- 无符号类型的右移补0；本课程通常实现中的有符号负数右移采用算术右移，教材所用传统C规则将负数右移的结果留给实现定义。

### 1. 对，在这段代码的课程假设下自动补位

**不需要另写代码去补1或补0。** 不过，不能只看到 `>>` 就认为无论什么类型都补符号位；要检查左边真正参与右移的表达式。

原语句：

```c
return (x + (x < 0 ? bias : 0)) >> k;
```

x、bias和常量0都是int，因此括号中的和也是有符号int。为了阅读，可以把同一计算过程拆成：

```c
int t = x + (x < 0 ? bias : 0);
return t >> k;
```

这只是等价的讲解写法，不是必须增加的处理步骤。按课程实现假设，t为负时，右移自动在左侧补1；t非负时补0。

| 被右移的左操作数（提升后） | 左侧补什么 |
|---|---|
| unsigned int | 补0 |
| 本课程实现中的负int | 复制最高位，即补1 |
| 非负int | 补0；此时逻辑、算术右移的位结果相同 |

这里的int本身已经是实际参与运算的类型。对于char、short等窄类型，还要先检查整数提升，不能直接看变量原来的位宽或有无符号。

### 2. −19除以8的实际步骤

取x=−19、k=3：

```text
bias = (1 << 3) − 1 = 8 − 1 = 7
x为负，因此选择加上bias
t = −19 + 7 = −12
然后计算t >> 3，即−12 >> 3
```

−12是32位有符号int，其补码最高位为1，因此右移3位时左侧自动补三个1：

```text
−12：11111111 11111111 11111111 11110100
                         >> 3
 −2：11111111 11111111 11111111 11111110
```

右边被移出的3位丢弃，左边新空出的3位填1。结果为−2，即−19/8在C中的向零截断结果。

### 3. bias修正的是取整方向，不是负责补符号位

“自动补符号位”是算术右移本身的行为，即使不加bias也会发生。bias解决的是另一个问题：

| 算式（按课程负数算术右移假设） | 结果 | 原因 |
|---|---:|---|
| `-19 >> 3` | −3 | −19/8=−2.375，算术右移向下取整 |
| `-19 / 8` | −2 | C整数除法向零截断 |
| `(-19 + 7) >> 3` | −2 | 先加偏置，把右移结果修正为所需的除法结果 |

因此代码要做的额外处理是**为模拟C整数除法加偏置**，不是手工制造算术右移的补位。

### 4. 复制相加后那个值的最高位，不固定复制原始x的最高位

`>>` 左边是相加后的t，复制的是t的最高位。

例如x=−1、k=3时：

```text
bias = 7
t = −1 + 7 = 6
t >> 3 = 6 >> 3 = 0
```

虽然原始x为负，但t已经为正，所以此时右移左侧补0。结果仍正确：C中的−1/8向零截断为0。不能看到函数最初传入负数，就认定最终这次右移一定补1。

### 5. 为什么代码第一行要写“本课程负数算术右移假设”？

教材采用的传统C规则将负有符号整数右移的结果规定为实现定义，而不是对所有C实现统一保证算术右移。本课程的通常实现采用符号扩展式右移，因此这段代码在该前提下可直接使用 `>>`。

GCC文档明确说明其负有符号整数右移采用符号扩展。可回查 [GCC整数实现说明](https://gcc.gnu.org/onlinedocs/gcc/Integers-implementation.html)；语言层次参见 [C11标准草案N1570，6.5.7](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)。这些是实现与语言规则，不是教材页码。

编译器根据表达式类型及其实现规则生成相应机器代码；x86算术右移指令sar会复制最高位，逻辑右移指令shr补0。优化后的具体代码不必逐行照搬源程序，但要满足相应语义。学习当前例题时不需要手工写汇编或掩码补位。

## Q012：读eax与写eax有什么区别，为什么只有写才清高位？

- 提问日期：2026-10-08（Asia/Shanghai）。
- 用户原始问题：“读 eax 不会清高位，**写 eax 才会 读与写的区别是什么**”
- 用户指定位置：复习第1讲，第8节「汇编入门：先读宽度，再读源与目的」，具体句子位于8.1末尾。
- 出处：主讲义8.1的子寄存器写入规则，并对照8.2的数据传送说明；对应原课程第4讲、教材3.4.1—3.4.2。精确教材印刷页码、PDF页序及课件页序待核实。
- 解答性质：助手补充，采用x86-64的64位模式与AT&T汇编语法。以下各例分别从给定初态执行，不是连续执行。

### 1. 读是取出已有内容，写是把结果存进去

**读eax：取出eax现在的内容，作为指令需要的数据。写eax：把一个结果存入eax，作为执行后的内容。**

可以类比纸上的数字：看一眼、抄走一份是读；往这个位置填写数字是写。读取本身不会把原内容清空。

eax是rax的低32位，并不是与rax无关的独立盒子。假设初态：

```text
rax = 0x11223344 55667788
         高32位    低32位＝eax
```

上面的空格仅用来分组。完整rax为 `0x1122334455667788`，eax为 `0x55667788`。

### 2. 读eax的例子：movl %eax, %ecx

```asm
movl %eax, %ecx
```

AT&T的mov写法是左边来源、右边目的。这条指令取出eax的32位内容，复制到ecx。

- 对eax：它提供数据，发生的是读；rax保持 `0x1122334455667788`。
- 对ecx：它接收数据，发生的是写；ecx得到 `0x55667788`，对应rcx的高32位自动清零，因此完整rcx成为 `0x0000000055667788`。

所以同一条指令可以“读一个寄存器、写另一个寄存器”。不能因为指令中出现了eax，就认为rax高位一定会被清零；要看eax在指令中做什么。

### 3. 写eax的例子：movl $5, %eax

```asm
movl $5, %eax
```

`$5` 表示立即数5；指令把5写入eax。结果为：

```text
执行前：rax = 0x11223344 55667788
执行后：rax = 0x00000000 00000005
                 自动清零   写入5
```

**写32位通用寄存器，会把对应64位寄存器的高32位清零，这是x86-64规定的效果。** 不需要程序员再写一条清零指令。这里说的“高位”特指rax的高32位，不是说把eax自己的高几位另外清掉。

### 4. 写回同一个值，也算写

```asm
movl %eax, %eax
```

它先读eax，再把这个值写回eax。从同一个初态开始：

```text
执行前：rax = 0x1122334455667788
执行后：rax = 0x0000000055667788
```

虽然eax低32位的内容没有变，写入动作仍发生了，所以rax高32位仍要清零。**判断依据是指令有没有写eax，不是执行前后eax数值是否相同。**

### 5. 一条指令也可以同时读写eax

```asm
addl $1, %eax
```

它先读取eax旧值，加1，再把32位结果写回eax。因此它既读eax又写eax，最后也会清零rax高32位。

| 指令 | 对eax的操作 | rax高32位是否因此清零 |
|---|---|---|
| `movl %eax, %ecx` | 只读eax | 否；写入的是ecx |
| `movl $5, %eax` | 写eax | 是 |
| `movl %eax, %eax` | 先读再写eax | 是，即使低32位不变 |
| `addl $1, %eax` | 读旧值并写回结果 | 是 |

这条清高位规则针对32位通用寄存器写入。不要把它扩大成“写任何宽度都会清高位”；写al、ax的规则不同，见主讲义8.1。

### 1. 前半句基本正确，后半句需要改成“寄存器里的值”

**`%rdi` 表示rdi寄存器；作为来源时，直接读取寄存器里的值。这个值可以是地址，也可以是普通整数。**

**在这里的mov指令中，`(%rdi)` 表示把rdi里的值当地址，访问那个位置的内存。** 作为来源时读取内存，作为目的时写入内存。因此“取地址中的数”适合描述它作为来源的情况。

### 2. 同一个初态，看两种来源各取到什么

假设rdi中存着 `0x1000`，从内存地址 `0x1000` 开始的8字节存着整数5（小端字节依次为 `05 00 00 00 00 00 00 00`）。以下两条指令各自从这个初态执行：

| 指令 | 读取来源 | 执行后rax的值 |
|---|---|---|
| `movq %rdi, %rax` | rdi寄存器里的64位值 | `0x1000` |
| `movq (%rdi), %rax` | 以rdi的值为起点的8字节内存 | `5` |

第一条像看纸条上的门牌号，第二条像按照门牌号找到房间，再取房间里的东西。两条指令都不会改变rdi；在这个例子中，rdi都仍是 `0x1000`。

这里取8字节，是因为movq的q指定8字节宽度，**不是因为括号本身指定8字节**。例如movl从相同地址读取的是4字节。

### 3. 为什么不能说%rdi“只表示地址”？

如果一段程序把普通整数37放在rdi里，读取 `%rdi` 就得到37。寄存器的名字不会自动给内容贴上“地址”或“普通整数”的标签，含义要看程序怎样使用它。

若此时在mov中使用 `(%rdi)`，就会把37当作内存地址去访问，而不是直接得到整数37；该地址能否访问又是另一回事。

此外，括号本身也不等于“读取”：`movq $5, (%rdi)` 是把5写到rdi指向的8字节内存，rdi本身不变。可记为：**没有括号，操作寄存器；当前mov语境下带括号，操作寄存器指向的内存。**
